# Redis value inspector

Extends the key browser with paginated hash, list, set, sorted-set and stream
views. Strings have Text, JSON, Hex and quoted-byte editing views. JSON formatting
preserves number lexemes, escapes and object key order; syntax spans are prepared
on the worker, including strings spanning bounded display lines. Copy uses the
original/pretty source rather than inserting display wraps into data.

Controls now share SQL’s compact button styling, segmented tabs and existing
Lucide artwork; see REDIS-ROADMAP.md for the subsequent shared styling pass.
The toolbar has 16-point horizontal and 10-point vertical margins. Format buttons
share widths; paging buttons share widths and icons. Complete strings omit paging
controls. Metadata stays compact; input fields align with their adjacent actions.

## Behavior and limits

- Lists and score-ordered sorted sets use 200-entry ranges. Streams request 201
  entries, retain 200 and resume exclusively after the last retained ID.
- Hashes, sets and filtered sorted sets use SCAN-family cursors with COUNT 200.
  COUNT is a server hint, not a page-size guarantee. Empty intermediate batches
  still expose Next. Matching sorted sets use scan order rather than score order.
- List/stream filtering applies only to the current page. Hash field and set/zset
  member matching is server-side and supports quoted binary glob patterns.
- Previous history commits only after successful reads and retains at most 512
  cursors. These are live reads, not a snapshot; concurrent changes can affect
  traversal and counts.
- String pages contain at most 64 KiB. Partial strings are read-only. Existing
  whole-string compare-and-set and expiry preservation remain in effect.
- Retained collection previews have a 256 KiB/8192-node budget and a 64 KiB
  individual-value limit. Oversized responses display a warning; skipped data is
  not represented as complete. These bounds apply after the Redis driver decodes
  the response, not to wire response size. Redis SCAN can return oversized batches.
- Value rows and text lines are virtualized. Each display line is bounded to 256
  characters; JSON formatting has a 512 KiB output cap. Details use bounded full
  values while table cells use short previews. No database work runs on the UI
  thread. Collections are read-only; RedisJSON is not implemented by this change.

## Protocol and latency

Trace: `inspect_view` pipelines TYPE/PTTL, then `read_value_page` pipelines
length/data. Subsequent pages pipeline TYPE/PTTL/length/data together and validate
the returned type. The existing Redis pipeline writes the batch before consuming
all responses; no health check or new connection is added. Initial reads require
the type to select the correct length/read command. Missing keys need one exchange.

On established connections, cold and repeated existing-key inspections change
from four sequential exchanges (TYPE, PTTL, length, data) to two. Each subsequent
page/search uses one exchange. Connection authentication/TLS/SSH setup is unchanged
and outside these established-connection counts. No shared PostgreSQL or MySQL
execution path was modified; their protocol sequences are unchanged.

The fake RESP test withholds responses until each expected batch arrives, covers
initial and repeated opens, sparse scan batches, type-change errors and connection
reuse. Disposable Redis tests cover 701-item collections, 201 stream entries,
70,000 binary string bytes, empty/missing keys and filtering.

## UI validation

Native framebuffer screenshots are generated by
`scripts/preview-redis-browser.sh` with `RUSTABLE_REDIS_INSPECTOR_CAPTURE=1` and
`RUSTABLE_REDIS_CAPTURE=<directory>`. The script owns a disposable Redis container
and removes it on exit. It does not load saved connections. Screenshots cover
first/next list pages, highlighted JSON, sorted sets, streams and hashes.

Performance comparison uses local pre-inspector snapshot
`b6c6ef482ee6683989c36932837b0e343c7b86b3`, preserving the already-completed key
browser work. `scripts/ui-performance.py --redis` copies identical grid, hash,
large-string and full-browser workloads into both revisions. Inspector workloads
apply the same browser style entry point; the full-browser workload covers toolbar
and filter controls. The candidate-only format-switch workload exercises Text,
JSON and Hex, including first use and the first switch after an idle time gap.

Native interactive, input-to-display, 60/120 Hz, mixed-DPI, snapping and multiwindow
checks remain unavailable while the desktop is locked. CPU measurements and native
framebuffer captures do not establish those properties.

22 of 23 comparison metrics passed, including every existing SQL UI metric. The
hash inspector is an **accepted regression**: +16.1% p95, or +.004666 ms, repeatable
in all five pairs. The report retains its regression and exit-1 status. The
threshold, fixtures and sample counts were not weakened. This is separate from
the earlier browser milestone's hash-layout cost documented in REDIS-BROWSER.md.

The hash path now renders search, cursor navigation and completion feedback as
well as selectable structured rows. Inspection of the render path attributes the
added work to those extra immediate-mode controls; rows are already formatted on
the worker and only visible rows are rendered. The concrete benefit is discovering
fields beyond a fixed preview and safely navigating server-side search results.
Hiding navigation when disabled was considered but would shift the search and
rows between page states. Custom-painting controls would reduce widget work but
would require reproducing focus, disabled state and accessibility behavior. The
stable, functional controls justify the measured extra cost; merely fitting a
frame budget is not the justification. No full-collection rendering or network
work was introduced on the UI thread.

Large-string p95 improved 90.3% through bounded, virtualized display lines and a
cached original quoted representation for unsaved-edit checks. The separate
format-switch workload (`target/redis-value-modes-performance.log`) measured
p50 .052459 ms, p95 .082291 ms, p99 .289250 ms, maximum .296375 ms across 160 frames.
Its nine first/switch samples include a 3.430333 ms cold first render; switch-sample
p50 was .135000 ms and maximum/p95 was 3.430333 ms. The fixture uses 500 Unicode
JSON items and programmatic Text/JSON/Hex changes, including an idle time gap. It
also asserts that switching display modes never changes editable bytes. These
small switch samples have no pre-feature baseline and do not measure actual
pointer/input-to-display latency.
